  ~1.5 DAYS OF NATURAL CADENCE NOW CHECKED (2026-07-16, Sonnet 5,
  Addendum 2): F5 CONFIRMED — 424 ticks since the restart (190
  assertion, 234 exploratory), 100% parse_ok both sides, 0 quarantine
  events. F6 NOT FIXED — 22 new self-initiated explorations, 21/21
  closures were budget_exhausted (0 nova_close), every one stopping at
  exactly ticks_used=11/12 and ~3627-3639s elapsed, matching the
  pre-fix pattern exactly. This is arithmetic, not a parsing issue:
  max_ticks(12) x tick_interval(300s) = wall_clock_seconds(3600)
  exactly, so a 12th tick always needs real time already past the
  wall-clock budget by the time dispatch overhead is accounted for —
  independent of how fast or clean each tick's generation is. The one
  "nova_close" reported right after the restart (Addendum 1) is now
  understood as a methodology artifact: it came from 12 manually-fired
  `!tick` commands in under two minutes, never actually exercising the
  wall-clock gate (which only binds after ~3600 REAL seconds). It
  proved the mechanism works when the model reaches tick 12, not that
  natural cadence reaches tick 12. Net: Tier 1 is done and confirmed;
  **Tier 1b (wall_clock_seconds/max_ticks/tick_interval reconciliation)
  is now the sole, clearly-identified remaining blocker on F6** — not
  optional/secondary as the original three-tier framing implied, but
  the actual next step if F6 is to be resolved. Still blocks Stage
  22.4's ladder-progression procedure (part b): the only claim_ladder
  record that exists is still the one from the artificial test, not a
  natural one. One minor side effect recorded, not a defect: an
  exploration open in yesterday's session at restart time is
  permanently stranded in status="active" (no code path interrupts
  cross-session-boundary orphans) — harmless, noted for whenever
  daemon-restart/session-rotation logic is next touched.
