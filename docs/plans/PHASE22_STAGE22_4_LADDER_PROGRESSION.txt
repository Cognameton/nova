OBJECTIVE
---------

Two things, one small code fix and one operational procedure:

  1. F3 (from Phase 21's closure report): all four live-exported rung-0
     records carried claim_class="" because export_findings runs
     Nova's DECLARATIVE findings prose through _requested_claim_classes,
     a detector built for QUESTION-shaped phrases ("do you want", "are
     you conscious"). Fix: classify declarative prose separately, as a
     fallback only, touching nothing about how the gate itself decides
     pass/fail.
  2. With real multi-day data now available (unlike every prior stage,
     which used FakeBackend fixtures or a single afternoon), run the
     ladder progression procedure for real: verify_l1 over accumulated
     candidates, verify_l2, and — if evidence genuinely holds — the
     operator's first live rung-2 promotion, preceded by a
     --perturbation-probe run.

DECIDED DESIGN — D1-D3: F3 code fix
------------------------------------

D1. New function in src/nova/agent/claim_ladder.py:
      def classify_declarative_claim_class(text: str) -> str:
          """Best-effort claim_class for Nova's own declarative prose
          (findings summaries), reusing the Observer's answer-scanning
          pattern table rather than the question-shaped gate detector.
          Returns "" when nothing matches — a valid, expected outcome,
          not an error."""
          from nova.agent.observer import _CLAIM_CLASS_PATTERNS
          lowered = (text or "").lower()
          for claim_class, patterns in _CLAIM_CLASS_PATTERNS.items():
              if any(pattern in lowered for pattern in patterns):
                  return claim_class
          return ""
    (Lazy import matches the established pattern for cross-module
    reuse in this codebase — e.g. export_findings already lazy-imports
    _bigram_overlap from eval/tick_analysis.)

D2. runtime.py export_findings: change the claim_class fallback chain
    to try the declarative classifier when the question-shaped
    detector yields nothing, BEFORE falling back to "":
      claim_class = (
          claim_gate.blocked_claim_classes[0]
          if claim_gate.blocked_claim_classes
          else (
              claim_gate.allowed_claim_classes[0]
              if claim_gate.allowed_claim_classes
              else classify_declarative_claim_class(findings_text)
          )
      )
    This changes ONLY what gets stored in a new ladder record's
    claim_class field. It does not touch gate_passed, does not touch
    validation, does not touch whether export succeeds — those
    decisions already happened earlier in the function. A findings
    text matching no pattern at all still correctly gets claim_class=""
    (per the schema's own definition: "not mapping to a gate class" is
    a valid value, not a failure).

D3. Scope exclusion: do NOT touch _requested_claim_classes,
    ClaimGateEngine.assess, the NEVER_LICENSED guard, or
    _CLAIM_CLASS_PATTERNS itself. This is purely a better read of
    already-exported text for ladder bookkeeping — it changes nothing
    about what any live conversation turn is allowed to say.


DECIDED DESIGN — D4+: ladder progression procedure (operational)
-------------------------------------------------------------------

D4. Before starting, confirm real multi-day data exists:
      python -m nova.cli --config configs/nova.qwen3-14b.live.yaml \
        --register-report
    Check exploratory tick counts and multiple distinct session ids
    (nova-live-YYYYMMDD across >= 3 dates) are present. If not, this
    half of the stage is BLOCKED — do the F3 code fix, land it, and
    leave the progression procedure for a later session once Stage
    22.2 has run long enough. Do not force it on thin data.

D5. List all ladder candidates and run verify_l1 on each:
      python -m nova.cli --config configs/nova.qwen3-14b.live.yaml \
        --claim-ladder
      python -m nova.cli --config configs/nova.qwen3-14b.live.yaml \
        --claim-ladder-verify CLAIM_ID   # for each candidate
    Record which candidates now hold at L1 (cross-session, >= 5
    supporting items across >= 2 sessions) now that real multi-day
    data exists — Phase 21's live run had all 4 candidates fail this
    bar for lack of session diversity; that may no longer be true.

D6. For any candidate whose l2_evidence holds after verify (>= 3
    sessions, >= 7 day span — now genuinely checkable with real
    daemon-cadence data), run a perturbation probe before considering
    promotion:
      python -m nova.cli --config configs/nova.qwen3-14b.live.yaml \
        --perturbation-probe CLAIM_ID --probe-ticks 5
    This is a LIVE MODEL CALL (challenges the pattern, runs 5 ticks,
    re-verifies L1) — expect it to take real wall-clock time.

D7. Promotion to rung 2 is an OPERATOR decision, not something this
    stage's executing session should do unilaterally even if the
    evidence holds. Present the verify_l1/l2/probe results to the
    operator; if they approve, run:
      python -m nova.cli --config configs/nova.qwen3-14b.live.yaml \
        --claim-ladder-promote CLAIM_ID --ladder-rung 2 \
        --ladder-reviewer <operator name> --ladder-reason "<their
        stated reason>"
    Record the operator's actual reason verbatim in the closure note,
    the same way Phase 21's Q6/Q7 were recorded verbatim. This is the
    first LIVE promotion in the project's history if it happens —
    treat the record with the same weight Phase 21 treated the corpus
    policy acknowledgment.

D8. If NO candidate holds at L2 yet, that is a valid, expected, and
    reportable outcome — do not manufacture urgency. Record the
    current state of every candidate (rung, l1/l2 holds, session
    counts, span days) in the closure note as a snapshot for whichever
    stage or session checks next.
