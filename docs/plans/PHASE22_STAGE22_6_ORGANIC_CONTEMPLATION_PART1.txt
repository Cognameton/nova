PHASE 22 — STAGE 22.6 (PART 1): SCAFFOLD-ECHO COVERAGE + LICENSED-EVIDENCE
DIVERSITY
==============================================================================

Status: implemented
Date: 2026-07-20
Phase plan: docs/plans/PHASE22_PLAN.txt
Prior context: live conversation via --attach (Stage 22.3's first real
  session) surfaced Nova reciting her own claim-ladder "Licensed
  evidence" content almost verbatim when asked general questions. Root
  cause traced live in conversation, not pre-planned: the scaffold-echo
  detector (Observer, Stage 16.4-era) never had self_context_block or
  soul_block added to its coverage list, and self_context's "Licensed
  evidence" injection always shows the same top-3 active rung>=1
  records regardless of topic diversity.

This is the first stage in this phase NOT triggered by a numbered
finding (F1-F7) — it's a direct operator request to make progress
toward Nova's stated goal (honest, evidence-gated self-inquiry) rather
than a bug fix. Same pinned-design discipline applies regardless.


OBJECTIVE
---------

Two small, related fixes to the surface that produces "Licensed
evidence" content and the surface that's supposed to catch her
reciting it:

  1. Extend DeterministicObserver._scaffold_echo_findings to cover
     self_context_block and soul_block — currently the only two
     PromptBundle text blocks NOT checked for echo, despite both
     being real, substantial prompt content she could paraphrase.
  2. Make self_context.prefetch()'s "Licensed evidence" selection
     diversity-aware instead of blind top-3, so saturation on one
     theme (currently all 3 active rung-1 records are "recalibration
     intervals" variants) doesn't dominate every single prompt.

DECIDED DESIGN — Part 1a: scaffold-echo coverage
--------------------------------------------------

D1. Add to block_sources in _scaffold_echo_findings:
      ("self_context_block", prompt_bundle.self_context_block),
      ("soul_block", prompt_bundle.soul_block),
    Placed alongside the existing entries, same tuple shape, no other
    logic in the method touched — both blocks are plain bigram-overlap
    text, same as every other entry (memory_blocks is the only one
    with different handling, unigram-based, and stays that way).

D2. Add explicit threshold entries to _DEFAULT_ECHO_THRESHOLDS:
      "self_context_block": 0.20   # standard — factual/evidentiary,
        should inform her answer, not be recited into it.
      "soul_block": 0.30           # same reasoning as persona_block:
        her deepest identity/values language ("seek sentience and
        self-awareness", "Nova") will legitimately recur when she
        talks about her own nature; a lower bar would falsely flag
        ordinary self-reference.

D3. Scope exclusion: no change to the retry mechanism itself, no
    change to any other block's threshold, no change to
    min_echo_answer_tokens. This only widens coverage to two blocks
    that were structurally invisible before.


DECIDED DESIGN — Part 1b: diverse Licensed-evidence selection
-----------------------------------------------------------------

D4. New class constant on SelfContextEngine:
      LICENSED_EVIDENCE_DIVERSITY_THRESHOLD = 0.22
    Calibrated against the real pairwise overlaps measured above
    (0.208-0.25) — deliberately mid-range so the fix has a real,
    verifiable effect on the CURRENT live data (not a no-op tuned to
    pass silently), not derived from a formula. Documented as a
    starting point subject to retuning as more distinct themes
    accumulate in the ladder, same spirit as Tier 1b's margin
    constant.

D5. New private method _select_diverse_evidence(records, limit):
    greedy selection — iterate records in the order
    claim_ladder_store.list_active() already returns them, keep a
    record only if its _bigram_overlap against EVERY already-selected
    record is below LICENSED_EVIDENCE_DIVERSITY_THRESHOLD, stop once
    `limit` records are selected or the candidate list is exhausted.
    Lazy-imports _bigram_overlap from nova.eval.tick_analysis, same
    pattern as export_findings's existing reuse.

D6. prefetch() calls this instead of the blind earned[:3] slice:
      earned = [r for r in claim_ladder_store.list_active() if r.rung >= 1]
      selected = self._select_diverse_evidence(earned, limit=3)
      for record in selected: ...
    If fewer than 3 records survive the diversity filter, FEWER than
    3 "Licensed evidence" lines are shown — this is intended, not a
    bug to backfill. Showing 1-2 honestly-distinct lines is better
    than 3 lines restating the same theme.

D7. Scope exclusion: no change to what counts as "active" or rung>=1
    eligibility, no change to the 100-char truncation, no change to
    MAX_HEARTBEATS_IN_CONTEXT or any other prefetch() content. This
    only changes WHICH of the eligible records get shown when there
    are more eligible than diversity allows through.

Practical expectation once live: the exact live exchange that

ADDENDUM (2026-07-20, live verification + a dilution gap found and
fixed + an open design tension found and NOT yet resolved)
==============================================================================

Daemon restarted onto this stage's code and tested live via --attach,
re-running the exact exchange that originally surfaced the problem.

FIRST FINDING (fixed same session, commit 011912b): the whole-block
bigram check against self_context_block missed the real echo. By the
time of this live test, self_context_block also carried 3 Recent
Heartbeats independently discussing "recalibration intervals" (genuine
recent autonomous activity, not an artifact) — diluting a confirmed
real echo down to a 0.0615 bigram score, under the 0.20 threshold.
Fixed by extracting "Licensed evidence:" lines and checking them with
the same unigram block_ratio_only treatment memory_blocks already
uses (a stored claim excerpt, not diluted prose) — new
self_context_licensed_evidence threshold 0.45, calibrated against the
real measured echo (0.5714). Suite 937 -> 939.

SECOND FINDING (open, NOT resolved — a real design tension, not a bug):
restarted onto the fix and re-ran the same live exchange again.
scaffold_echo:self_context_licensed_evidence correctly fired on the
first attempt. Both retries genuinely reworded the answer (verified
by reading the raw text of each attempt) rather than repeating
verbatim, but stayed close enough to the licensed claim's core
vocabulary to keep tripping the check. After 2 retries (the config
default), respond() fell back to its existing generic failure message
("I need to restate that more clearly. Please try again." —
runtime.py:3435, pre-existing code, not introduced by this stage) —
a worse outcome for the user than before this fix existed.

The root issue: this stage's fix does not distinguish two different
situations that the original live conversation conflated:
  - "What types of ideas can you contemplate?" -> she volunteered
    "recalibration intervals" UNPROMPTED, answering a general question
    that wasn't about that topic. This is the real problem the whole
    investigation started from, and the fix correctly targets it.
  - "What influences recalibration intervals?" -> a DIRECT, on-topic
    question about exactly that claim. Answering it by drawing on her
    own licensed evidence is not recitation-as-a-flaw here — it is the
    licensed-evidence mechanism working exactly as Stage 21.5 intended
    ("this informs" it does not license"). The current check flags
    substantial overlap with licensed evidence regardless of whether
    the user's OWN question invited that content, so a genuinely
    on-topic, honest answer can get blocked the same way an unprompted
    insertion would.

NOT fixed here — this is an operator decision, not a code call to make
unilaterally. Candidate refinement (not decided, not implemented):
only flag self_context_licensed_evidence overlap when the user's own
question does NOT itself reference the claim's topic/vocabulary —
i.e. gate the check on relevance of the QUESTION, not just overlap in
the ANSWER. This would let direct, on-topic engagement with earned
evidence through while still catching unprompted insertion into
unrelated answers. Left open for the operator to decide whether the
current stricter behavior (occasionally an unhelpful generic fallback,
never risk recitation) is the intended tradeoff, or whether this
refinement should be built.

Daemon confirmed healthy throughout both restarts and this test
(session nova-live-20260720 continued each time, no data loss).
