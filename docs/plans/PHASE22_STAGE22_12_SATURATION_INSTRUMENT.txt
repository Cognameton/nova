ORDERING NOTE
-------------

This stage lands BEFORE 22.11 on purpose. 22.11 and every arm after it is
judged on whether topic diversity recovers. Until that is measurable in a
window, no arm is readable — which is exactly how the collapse below ran
unnoticed for six days.


Findings recorded by this stage: F12 (total exploration-topic lock, three
eras) and F13 (all-time averaging hid it from the instrument). Both are
registered with full evidence in docs/RESEARCH_LOG.md, which from 2026-08-29
is this project's findings index and timeline. Reproduce the numbers with
scripts/analyze_saturation.py. Independent review of both findings and of
this stage's code: docs/reviews/2026-08-29-codex-review.md.


WHY (the finding this stage exists to prevent recurring)
--------------------------------------------------------

On 2026-08-29 an audit of the exploration record (1,077 explorations,
2026-07-12 -> 2026-08-29) found three eras:

  Era 1  Jul 12-23   healthy      10-19/day, distinct == opened (100% unique)
  Era 2  Jul 24-Aug 17  semantic lock   ~35/day, 24-37 distinct — surface
                                   rewordings of one theme ("scaffold void
                                   resonance", entering Jul 24)
  Era 3  Aug 23-now  TOTAL lock   distinct == 1 EVERY day; 125 consecutive
                                   explorations on one byte-identical topic,
                                   zero escapes, first seen 2026-08-23T13:25:53

Throughout era 3, --tick-analysis reported exploration_novelty_rate 0.645
and raised no flag, because that metric is an ALL-TIME average and the
healthy July era dominated the mean. observation_echo_rate likewise read
0.333 all-time while the recent window was running 0.83 — above the 0.7
threshold this file has described as "the primary early-warning signal"
since Phase 20. The instrument had the right idea and the wrong scope.

The 6 dark days (Aug 18-22) are already explained by finding F11 in the
22.9 doc: 22.8b went live Aug 17 and Nova stopped entering explorations
entirely. She resumed on Aug 23 already fully collapsed.

Lesson, generalised: a metric meant to catch a COLLAPSE must be scoped to
a recent window and must carry a worst-case statistic beside the average.
An average over a system's whole life cannot detect that the system has
stopped.


WHAT LANDED
-----------

src/nova/eval/tick_analysis.py, deterministic and stdlib-only like the
rest of the module (no embedder, no model, no GPU — this must be runnable
while the GPUs are busy, which is when it is most needed):

  SATURATION_WINDOW_DAYS = 7   (daily rotation cadence, 3-day arm reads)

  TickAnalysisReport gains:
    saturation_window_days       int
    topics_opened_recent         int    explorations opened in the window
    topics_distinct_recent       int    distinct topic strings among them
    topic_diversity_recent       float  distinct/opened; 1.0 healthy, ->0 collapsed
    topic_top_share_recent       float  share held by the commonest topic; 1.0 = total lock
    topic_repeat_streak          int    trailing run of identical consecutive topics
    observation_echo_rate_recent float  compute_echo_rate over the window only

  TickHistoryAnalyzer gains:
    compute_topic_saturation(explorations, window_days=7)
    compute_recent_echo_rate(heartbeats, window_days=7)

  Three new quality flags in report.reasons:
    topic_collapse=...        diversity <= 0.34 over >= 5 explorations
    topic_repeat_streak=N     N >= 10
    recent_echo_rate=...      windowed >= 0.7 while all-time < 0.7
                              (states explicitly that the average is masking it)

Design decisions worth keeping:

  1. The window is anchored on the NEWEST record, not wall-clock. The same
     data must produce the same report whenever it is run, and historical
     data dirs must still report rather than reading empty.
  2. topic_repeat_streak is computed over the WHOLE record, not the window,
     so a lock longer than 7 days reports its true length (125, not 7).
  3. Records with an unparseable opened_at are excluded from the window but
     still counted by the streak, which walks the store in file order and
     never sorts. Bad timestamps must not silently shrink the alarm, so the
     count of such records is reported as topics_undated.
     (As first written this was WRONG — see CORRECTIONS below, item 0.)

NOT IN THIS STAGE
-----------------

No behavior change of any kind. This stage only measures. The arms it
exists to make readable, in the order they should run (one at a time,
pre-registered metric = topic_diversity_recent + topic_repeat_streak,
3-day read, the cadence Part D established):

  Arm 1  recall_history default mode: recent -> sample. Cuts the within-day
         amplifier (22.10 Part A carryover feeds her own last 8 observations
         back into her next 2 tick prompts; she calls it 14/16x on
         heartbeats/recent).
  Arm 2  Stop rendering recent topic STRINGS in the topic-selection prompt;
         render only the constraint. Tests the priming hypothesis — F11
         established the tick loop is instruction-dominated, so showing an
         instruction-dominated loop the string it must avoid may be what
         pins it.
  Arm 3  Deterministic novelty gate: refuse in code to open an exploration
         whose topic is within threshold of the last N. Do not ask the model
         to be novel; refuse the duplicate. The embedder already exists.

Prompt-framing as a lever is spent: Part D (22.7 part D, activated 08-25,
eval read 08-29) was a clean null — no erosion, no benefit — and 22.7's own
"30 of your last 30 explorations pursued closely similar topics" warning has
never moved it either.


============================================================================
CORRECTIONS — independent review, 2026-08-29
============================================================================

An independent read-only review (Codex; handoff at
~/Dev/ai-lab/CODEX_REVIEW_HANDOFF_2026-08-29.md) checked both this stage and
the diagnosis that motivated it. It changed nothing; repo hashes verified
unchanged before and after. Its corrections, recorded here because several
of them contradict statements made above and in the memory record.

0. DEFECT IN THIS STAGE, NOW FIXED. topic_repeat_streak was documented as
   "order-based" but was in fact timestamp-sorted, with unparseable stamps
   sorting LAST — so a single malformed record at the tail could decide
   newest_topic and silently truncate a real lock to 1. Now genuinely
   order-based: it walks the store in file order and never sorts. That is
   also the runtime's own notion of recency (ExplorationStore.list_recent is
   _read_all()[-limit:], and no code path removes records). Added
   topics_undated so excluded records are never silent. Two regression tests;
   suite 1063 -> 1065. Live numbers unchanged (streak 125, undated 0) — the
   defect was latent on valid data, not active.

1. PROMPT PATH: VERIFIED, BUT THE REGISTER WAS NAMED WRONG. The recent-topic
   history block IS in the real topic-selection prompt — but that is the
   ASSERTION-register prompt, the one whose menu contains enter_exploration
   (runtime.py:1028 -> _exploration_history_block at runtime.py:893;
   register chosen at runtime.py:982). self_state_tick.py:207 explicitly
   SUPPRESSES the block once already in the exploratory register. Earlier
   text calling it "the exploratory-register tick prompt" is wrong.

2. NO BYTE-IDENTICAL PROMPT STRING. Topics render as record.topic[:90]
   (runtime.py:924); the locked topic is 91 chars and appears truncated.
   Semantic priming survives; any byte-identical claim does not.

3. THE BLOCK CANNOT EXPLAIN THE FIRST LOCKED TOPIC. Before 2026-08-23 the
   five displayed records were varied Aug-17 phrasings. The block becomes a
   plausible PERSISTENCE mechanism only after the fifth repeat. What sustains
   the lock and what started it were conflated.

4. CAUSAL ATTRIBUTION TO 22.9/22.10 IS UNSUPPORTED. The topic-history
   mechanism itself landed 2026-07-23 (2b767a7), immediately before the
   Jul-24 semantic-lock era. 22.9 changed three things at once: prompt
   wording, removal of /no_think, and application of 20 accumulated
   self-model proposals (current focus, active question) which reach every
   tick via SelfContextEngine.prefetch (runtime.py:1003); 22.9's own plan
   says 22.9-vs-22.10 attribution is impossible. The first exact topic was
   selected at assertion tick 100 immediately after a recall_self at tick 99
   whose result carried the newly applied focus plus five repetitive
   heartbeats (logs/traces/nova-live-20260823.operational.jsonl:99-100).
   The Aug-23 discontinuity is real; its cause is NOT identified.

5. "PART D WAS A CLEAN NULL" IS OVERSTATED. It is a short, uncontrolled null
   on the outcomes measured. "No drive erosion" is especially weak: the
   metric counts equality of a fixed motive_priority field
   (tick_analysis.py:103), not substantive persistence.

6. PROTOCOL. A 3-day single-arm read is a legitimate OPERATIONAL SCREEN —
   highly autocorrelated ticks make a total lock obvious fast — but it is not
   evidence of mechanism: no control, no randomization, no washout, and
   persistent state crosses day boundaries. Stronger: pre-register a
   prevention outcome separately from a mechanism outcome; randomize or
   counterbalance prompt variants BY DAILY SESSION, recording assignment,
   rather than comparing one chronological block against an earlier era;
   ABAB reversal only for reversible low-risk prompt arms; and evaluate the
   novelty gate as a safety/control property ("duplicates refused") rather
   than waiting three days on a behavioral read.

7. THE SYNTHIA PARALLEL IS OVER-READ AT n=4. The structure is real
   (synthia/heartbeat.py:240,262 inject the prior three thoughts) but the
   same prompt also injects self-state, skills, recent conversation and
   active wants (heartbeat.py:232), so the thought tail is not an isolated
   explanation. Cold start, sparse conversation context and idle-only
   prompting are adequate alternatives. Hypothesis-generating, not
   corroboration, and not a cross-architecture law.

8. REVISED ARM FRAMING. Arms 1 and 2 remain worth running but must be judged
   as "does this break PERSISTENCE?", not "does this establish root cause."
   If the goal is simply to stop duplicate work, Arm 3 (deterministic
   novelty gate) is the only assured control and arguably goes first.

STILL OPEN after this correction pass (not done):
  - exploration_staleness_days / wall-clock-anchored newest-exploration
    timestamp, plus a "no explorations in N days" alarm. Newest-record
    anchoring is right for reproducible history and wrong as the sole
    live-health signal: a fully stopped stream still reports its last active
    window as though current (the F11 dark-days case).
  - A SEMANTIC concentration companion to exact-string diversity, which
    catches era 3 but would have missed era 2 entirely. Reuse the existing
    cluster_texts helper (agent/self_context.py:10), built precisely to group
    reworded exploration topics; keep exact-string as the companion, not the
    replacement.
