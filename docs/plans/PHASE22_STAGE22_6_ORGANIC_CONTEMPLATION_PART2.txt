PHASE 22 — STAGE 22.6 (PART 2): BOUNDED THINKING-SPACE EXPERIMENT ON
respond()
==============================================================================

Status: implemented
Date: 2026-07-20
Phase plan: docs/plans/PHASE22_PLAN.txt
Prior context: Part 1 (docs/plans/PHASE22_STAGE22_6_ORGANIC_CONTEMPLATION
  _PART1.txt) closed a detection gap and a saturation problem. This part
  addresses the harder, more speculative hypothesis named in that same
  conversation: that Tier 1's enable_thinking=False (Stage 22.2b) fixed
  F5 by removing the model's deliberation space ENTIRELY, and that this
  may be part of why respond() answers lean so heavily on salient
  injected context (self_context, soul) instead of visibly working
  through something before answering.

This is explicitly labeled EXPERIMENTAL. It is a real, bounded test of
a real hypothesis, not a proven fix — the closure note must report
what actually happens, including "no detectable difference" or "made
things worse," honestly.


OBJECTIVE
---------

Reintroduce genuine model deliberation (native enable_thinking=True,
the same mechanism Stage 22.2b built) but ONLY on respond() — never on
model_self_state_tick or model_idle_tick — and only ever as an
ephemeral scratchpad: the <think> block must never reach the user,
never be persisted as the answer, never become memory or evidence.
Default OFF (opt-in via config), so this ships fully reversible and
inert until explicitly turned on.


WHY respond() SPECIFICALLY AND NOT THE TICK LOOP
---------------------------------------------------

model_self_state_tick has ZERO retry on parse failure (confirmed in
code comment, runtime.py, Stage 22.2b's own root-cause investigation)
— this is exactly why F5 was damaging there: a truncated or malformed
tick was simply lost. respond() already has three independent layers
of protection that self_state_tick does not:
  1. A real retry loop (retry_policy.should_retry, up to
     config.generation.retries attempts).
  2. Validator-level <think> handling that ALREADY EXISTS and already
     works correctly for the case that matters: _sanitize_completion_
     artifacts (validator.py:84-92) strips well-formed <think>...
     </think> blocks via regex BEFORE the think_tag_detected check
     runs against the ALREADY-STRIPPED effective_text (validator.py:
     32-45). A cleanly-closed think block does NOT trigger a
     violation — only an unclosed/malformed one does (the retry-
     worthy failure case). This was verified by reading the code, not
     assumed.
  3. Post Part 1: full scaffold-echo coverage across all 14 text
     blocks including self_context_block and soul_block.
No new stripping logic is invented here — the existing validator
mechanism is reused exactly as-is, matching the project's standing
discipline (Stage 22.4's F3 fix, Stage 21.4's NEVER_LICENSED guard,
etc. all reused existing mechanisms rather than inventing parallel
ones).


CODE FACTS (verified 2026-07-20 against commit f9c7ad5, suite 927
  green)
-----------------------------------------------------------------------

  - GenerationRequest (types.py) currently has no enable_thinking
    field — LlamaCppBackend.generate() hardcodes enable_thinking=False
    as a literal at the call site (llama_cpp_backend.py, Stage
    22.2b), applying uniformly regardless of caller.
  - _generation_request (runtime.py:4129) has exactly 4 call sites:
    line 968 (model_self_state_tick), line 2074 (model_idle_tick),
    line 3204 (respond(), initial generation), line 3280 (respond(),
    retry generation). It currently takes only prompt/messages and
    always uses self.config.generation.max_tokens uniformly for all
    four call sites — there is no per-surface override mechanism.
  - GenerationConfig (config.py:37-42): max_tokens=512, temperature=
    0.7, top_p=0.9, stop=[...], retries=2. No thinking-related fields
    exist yet.
  - Validator's <think> handling (validator.py): confirmed by direct
    reading — _sanitize_completion_artifacts strips <think>...</think>
    via re.sub(r"<think>.*?</think>", "", cleaned, flags=re.DOTALL)
    BEFORE the think_tag_detected check runs against the stripped
    effective_text. An UNCLOSED <think> tag (e.g. from hitting
    max_tokens mid-thought) will NOT be matched/stripped by that
    regex, leaving the literal "<think>" substring in effective_text,
    which DOES trigger think_tag_detected -> should_retry=True. This
    is the exact failure mode to budget against with a generous
    max_tokens override, not a new bug to fix.
  - run_perturbation_probe (runtime.py:1329) calls self.respond(
    counter_prompt) — it shares respond()'s code path entirely. This
    means enabling thinking on respond() will ALSO affect perturbation
    probes once live. This is a genuine, welcome side effect for the
    F7 investigation (a probe with real deliberation may produce a
    less templated defense), not scope creep — respond() is shared
    infrastructure and there is no clean way to exclude probes from a
    respond()-level change without inventing a second code path.


DECIDED DESIGN
--------------

D1. GenerationRequest (types.py) gains `enable_thinking: bool = False`.
    Default False preserves current behavior for every field that
    doesn't set it explicitly.

D2. LlamaCppBackend.generate() (llama_cpp_backend.py) reads
    `request.enable_thinking` instead of the hardcoded `False` literal
    when calling the native chat formatter:
      formatted = self._chat_formatter(
          messages=request.messages, enable_thinking=request.enable_thinking
      )
    No other change to generate() — the native-template vs. fallback
    branching from Stage 22.2b is untouched.

D3. New GenerationConfig fields (config.py):
      respond_enable_thinking: bool = False
      respond_thinking_max_tokens: int = 2048
    Both default to preserving exactly current behavior. Turning the
    experiment on live is a config-file change (one line in
    configs/nova.qwen3-14b.live.yaml), not a code change — this is
    deliberate: the mechanism ships now, activating it live is a
    separate, later decision, same pattern as every other stage this
    phase.

D4. _generation_request (runtime.py) gains two new optional
    parameters:
      def _generation_request(
          self, *, prompt: str, messages: list[dict[str, str]] | None = None,
          enable_thinking: bool = False, max_tokens_override: int | None = None,
      ) -> GenerationRequest:
    max_tokens_override, when provided, is used instead of
    self.config.generation.max_tokens; enable_thinking is passed
    straight through to GenerationRequest. Both default to values that
    reproduce EXACTLY today's behavior when omitted.

D5. model_self_state_tick (line 968) and model_idle_tick (line 2074)
    call sites are NOT touched — they keep calling _generation_request
    with only prompt/messages, so enable_thinking stays False and
    max_tokens stays the standard config value for both. This is the
    hard boundary this whole stage exists to respect.

D6. respond()'s two call sites (initial generation ~3204, retry
    generation ~3280) both compute:
      thinking_enabled = self.config.generation.respond_enable_thinking
      generation_request = self._generation_request(
          prompt=prompt_bundle.full_prompt,
          messages=prompt_bundle.messages,
          enable_thinking=thinking_enabled,
          max_tokens_override=(
              self.config.generation.respond_thinking_max_tokens
              if thinking_enabled else None
          ),
      )
    and identically for the retry_request construction using
    retry_prompt/retry_messages. Both the initial AND retry attempts
    get the larger budget when the experiment is on — a retry that
    also thinks needs the same headroom the initial attempt did.

D7. No new stripping/detection logic anywhere. Reuse validator.py's
    existing _sanitize_completion_artifacts and think_tag_detected
    check exactly as they already work (confirmed correct for the
    well-formed case in CODE FACTS above).

D8. Scope exclusion: no change to model_self_state_tick, model_idle_
    tick, run_perturbation_probe's own logic (it inherits the effect
    via respond() only), retry_policy, or the scaffold-echo mechanism
    from Part 1. No change to the live config's actual
    respond_enable_thinking value in this stage — it lands OFF,
    turning it on live is a separate decision.

ADDENDUM (2026-07-20, same session): TOKEN-BUDGET SHARING FALLBACK
======================================================================

Operator raised a specific, correct concern after this stage's initial
commit: max_tokens is ONE shared pool for think + answer tokens
together, not two separate budgets. As originally designed,
respond_thinking_max_tokens=2048 gave more headroom than the standard
512, but the RETRY used the identical enable_thinking=True + identical
budget as the attempt that just failed — meaning a prompt that
reliably induces long thinking could exhaust every retry attempt the
same way, ending WORSE than pre-experiment behavior (a complete but
imperfect 512-token answer beats an exhausted retry budget with
nothing usable). This is exactly the class of failure that made F5
damaging on the tick loop, just with a bigger budget delaying it
rather than a structural guarantee against it.

FIX (same commit as this addendum): within respond()'s retry loop, if
the attempt that just failed carries "length_truncated" or
"think_tag_detected" in its violations WHILE thinking_enabled is True,
the retry falls back to enable_thinking=False (and the standard
max_tokens, not the thinking-sized budget) instead of repeating the
same risky configuration. This is a one-way ratchet within a single
respond() call — once tripped, stays off for any further retries in
that call, even if a later retry fails for an unrelated reason (e.g.
scaffold-echo). This guarantees respond() can never end up worse than
its pre-experiment behavior: worst case, it falls back to the
proven-reliable Tier 1 mechanism on the very next attempt rather than
compounding the same risk across the whole retry budget.

No new mechanism invented — this reuses the existing violation types
(length_truncated, think_tag_detected) and the existing thinking_
enabled variable already threaded through both call sites.

3 new tests replace the 1 original (less rigorous) retry test:
  - a retry triggered by an UNRELATED failure (scaffold-echo, not
    truncation) keeps thinking enabled — the fallback is scoped
    specifically to truncation-shaped failures, not every retry
    unconditionally.
  - a retry triggered by a truncated/unclosed think block falls back
    to enable_thinking=False and the standard max_tokens.
  - the fallback stays off across a second retry even when that
    second retry fails for an unrelated reason (one-way ratchet,
    not a per-attempt re-evaluation).
One test-construction wrinkle, not an implementation bug: the first
attempt at the "stays off across further retries" test used a short,
artificial echo string that failed to trigger scaffold-echo detection
against the REAL, full persona_block (Values/Commitments/Style Rules/
Identity Anchors included, not just the short Core Description
excerpt used in an earlier hand-written reconstruction) — the real
block is long enough that a short echo snippet doesn't clear the 0.30
bigram threshold. Fixed by reciting a larger, verified-against-the-
real-block fraction of persona_block content, confirmed empirically
against the actual composed block before trusting the test, not
assumed. Suite: 935 -> 937.
